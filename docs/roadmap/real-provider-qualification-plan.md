## Outcome, sizing and dependencies

The outcome is one version-identified Proposal and one Acceptance **or**
Challenge responding to that exact Proposal through the production host,
adapters, parsers, persistence and protected inspection routes, with coherent
sealed evidence and unchanged fictitious repositories. A Challenge is valid;
forcing acceptance would invalidate the demonstration.

Group authentication comparison, bounded operator preparation, current evidence
projection, fresh allowance identity and the first exchange as one outcome.
Keep them in one future executor chat with internal gates rather than separate
micro-slices. Live A and B need separate execution decisions because A can
expose a missing authentication/environment prerequisite that changes B's
supported profile. It cannot be resolved by guessing environment keys.

Do not add a canary ladder with weaker flags: it consumes extra calls and
tests a different contract. The first model observation should exercise the
complete production read-only contract. Implementation, correction, Resolver,
coordinated local delivery, host-loss recovery, publication, CI and self-hosting
require different effects and evidence; they are subsequent outcomes.

Existing CLI-managed authentication is the selected starting direction. No
token forwarding, Desktop session extraction, credential copying or new login
method is selected. CLI-reported authentication is evidence of that context,
not proof of quota, model access or a historical cause.

## Preparation required before asking for real execution

The next proposed implementation is limited to the manual qualification
launcher/support, its focused offline tests and affected documentation. It
must return unstaged, uncommitted and unpushed for independent review.

1. Prepare A with direct typed arguments, no shell or TTY, the shared bounded
   process boundary, an ordinary owner-launched Windows terminal context and
   the actual production Claude environment builder. Do not duplicate the map;
   narrowly scoped internal access may be needed, without a public API or
   product policy change. Compare the same binary, user and disposable working
   directory. A helper started inside an executor does not establish equivalence
   with the owner's ordinary terminal.
2. Extend `StageReading`, `StageEvidenceReader`, `StageVerifier` and `SafeSummary`
   to include the recorded adapter contract version, required I/O completion and
   invocation diagnostic/version. The present schema-2 summary omits these
   ADR-0072 facts. Use a new summary schema; never rewrite schema-1/2 records.
   Read the attempt-evidence route even when no provider message exists, and
   compare the recorded facts without exporting streams or account data.
3. Give the future session a fresh, explicitly approved authorization identity
   and exclusive allowance location. The current `InvocationLedger` has a
   historical constant and fixed default path. Do not reset, archive, enumerate
   or read its old markers. Do not introduce an unrestricted path/authorization
   switch that silently bypasses the spent ledger. Consume each new allowance
   durably before its single POST; ambiguity never refunds it.
4. Inventory and enforce every host-issued process request, including automatic
   discovery. Preserve the production discovery and role adapters behind a
   qualification-only admission/counting boundary. Refuse unlisted commands
   before process creation; never silently suppress a required probe, invent
   readiness or substitute a provider fake in a real lot. Counters survive
   interruption for the one authorization; no restart or rearm is supported.
5. Rehearse deadlines, partial I/O, safe projection, refusal before dispatch,
   extra probes, duplicate entry, partial allowance consumption, missing/foreign
   attempts, evidence disagreement and shutdown uncertainty using owned doubles.
   One concise execution record per phase is sufficient; no new generic
   publication framework or per-command artifact campaign is selected.
6. Present the exact reviewed entry, source/binary identity, launch identities,
   context, commands, counts, evidence reads/writes, deadlines and stop actions
   for each lot before requesting its execution approval. No real discovery,
   version/help/status call or source-cache read is part of offline preparation.

Any production adapter/environment change revealed as necessary is a planner
decision and reviewed correction before dependent live work. Do not widen the
allowlist, remove a safety flag, increase `max-turns`, change model defaults,
install/update tools or repair authentication during a lot.

## Proposed call, time and usage envelope

All numbers below are proposed maxima, not current allowances. Actual call
inventory must be demonstrated offline before activation. Stop at the first
failed, refused, ambiguous, mismatched or expired step; never try another
context/model/binary as a fallback.

| Lot | Host-issued activity | Proposed ceiling |
|---|---|---|
| A: authentication comparison | Exactly `claude auth status`, once with the chosen ordinary terminal's environment and once with the production-filtered map; no model, version/help or other account command | At most 2 child starts, serial; 30 s execution each; existing 5 s post-kill and 5 s I/O plus 1 s release bounds; 2 min outer sequence including closure/report |
| B: read-only exchange | One Codex Planner invocation; only after its coherent Proposal, one Claude CriticalReviewer invocation for that exact Proposal | At most 2 model invocations; no retry, repair, Resolver, fallback, resume or compaction; existing 10 min invocation deadlines, 12 min per stage; 32 min active session, 60 s host shutdown, 35 min outer sequence including final observations/report |
| B: automatic discovery | Existing `--version` probes for Git, Codex, Claude, gh, .NET, Node and Docker; validated Node-script prefix only where production selects it | At most 8 per capability, 56 direct probe starts total; existing 5 s execution timeout each; no manual refresh, help, auth, account/model-catalog or GCM calls |
| B: fixture/source Git | Existing local fixture initialization, worktree/checkpoint preparation and read-only source comparisons | Closed typed command inventory with numerical per-command and total caps must be resolved from the launcher offline before B approval; no remote Git or helper invocation |

The discovery bound includes periodic refresh: the current supervisor records
the next probe five minutes after a result. The 35-minute outer envelope and
the count gate bound it even on scheduling differences. A changed discovery
behavior or an unlisted preparatory process blocks activation rather than
receiving an implicit allowance. Tool resolution/file identity checks themselves
must be bounded and restricted to the supported catalog or explicitly approved
exact launch identity; no profile search or app-private fallback.

The B fixture retains `maximumAgentAttempts=2` and
`maximumAgentInvocationMinutes=20`. Pin the actual CLI identities, selected
model/default policy, permission profiles and contract versions at review.
The current expected role contracts are `codex-planning-v1` and
`claude-critical-review-v3` (the flat transport schema of CLAUDE-REVIEW-SCHEMA-01; v2 was the contract when this plan was
written, see the [ADR-0072 extension](../decisions/0072-adopt-one-windows-execution-profile.md#narrow-extension-criticalreviewer-contract-v3-transport-schema));
the latter retains its complete restrictions and
`max-turns=1`. No model-catalog call is hidden in setup.

These bounds limit host-issued invocations and reserved time. They do not
enforce a monetary, token or provider-internal HTTP request ceiling; provider
retries/refreshes inside one invocation are not separate host calls. Usage
facts are reported only when observed, otherwise Unknown. No additional usage
probe is authorized. If the owner requires a hard monetary/token ceiling,
activation is blocked until an enforceable mechanism has been reviewed.
Managed deadlines assume a responsive OS; expiry never proves child or
descendant termination. No outer timeout authorizes killing unrelated processes.

## Lot A result and B admission

duration, I/O completion and comparison flags. Parse bounded in-memory output;
do not persist or display raw JSON, email, account ID, configuration path,
environment values or credentials. A configuration-directory equality flag may

([commands](https://learn.chatgpt.com/docs/developer-commands?surface=cli),
[authentication](https://learn.chatgpt.com/docs/auth)); no Codex status call is
included in A. These pages were consulted on 2026-11-02; they do not establish
the installed versions' behavior.

## Acceptance and evidence limits

- A qualifies only its two observations. Record physical completion separately
  from reported authentication. A logged-out report with the documented exit
  is a completed observation, never model readiness or evidence of no effects.
- B needs exactly the accepted attempts, their current contract versions,
  clean physical exits, explicitly complete required I/O, coherent role
  responses, one attributed message per role, exact ordered inputs/reply
  identity, agreeing protected evidence and all sealed length/hash comparisons.
  A missing or foreign attempt, historical contract or absent I/O fact fails.
- On a failed Claude invocation, read the recorded closed diagnostic/version
  through the existing attempt evidence. No text matching or raw-stream
  investigation is included. Unknown/generic diagnosis is a valid failure
  report, not a reason to retry or relabel it AuthenticationRequired.
- Independently compare source and worktree after every submitted stage and
  after bounded shutdown, including failed or ambiguous submissions. Unreadable
  is Unproven, never unchanged. No source or provider-policy drift is admitted.
- Report exchange compatibility, source integrity, invoked-process completion,
  descendant shutdown and cleanup separately. Retain the existing conservative
  process-table proof: OriginUnresolved preserves the new root and yields an
  attention result. It neither erases valid exchange evidence nor passes the
  full clean-session acceptance. No Job Object, process adoption, ownership
  release or relaxed cleanup proof is selected.
- Scope is only this Windows profile and these read-only roles. No claim of
  installed implementation/correction qualification, general reliability,
  authentication-cause proof, sandboxing, CI or self-hosting success follows.
