# Data and recovery

## Persistence strategy

The MVP uses event-sourcing-lite:

- immutable domain and operational events form the chronological audit trail;
- normalized materialized tables provide efficient current-state queries;
- an event and the materialized state it changes commit in the same SQLite
  transaction;
- external actions are represented by durable intent and immutable attempts.

This is not full event sourcing. The system does not require replaying every
historical event to construct normal runtime state, and event payloads do not
become the only schema.

## Core records

| Record | Responsibility |
|---|---|
| `Project` | Approved repository, configuration, capabilities, and policies |
| `Run` | One objective against an initial project and Git baseline |
| `Stage` | One workflow phase and its prerequisites |
| `Task` | One bounded unit of intended work |
| `Attempt` | One immutable agent, command, Git, or remote invocation |
| `ContextManifest` | Versioned bounded input selection for an agent attempt |
| `ProviderAllowanceSnapshot` | Time-windowed provider usage, reset, freshness, and confidence |
| `ConversationMessage` | Typed protocol message and references |
| `Challenge` | Disputed claim, evidence, status, and resolution |
| `Decision` | Explicit resolution and resulting action |
| `Review` | Review scope, Git fingerprint, evidence, and outcome |
| `Finding` | Review issue, severity, location, and disposition |
| `Approval` | Scoped authority for one consequential action |
| `GitWorkspace` | Worktree, branch, ownership, and current fingerprint |
| `RepositoryMutationLease` | Exclusive mutation ownership for a canonical repository |
| `GitCheckpoint` | Durable source and workflow recovery point |
| `RemoteChangeRequest` | Provider-neutral pull request state |
| `CheckSnapshot` | CI workflow, job, and check observations by head SHA |
| `Artifact` | Hash, media type, size, retention, and filesystem location |
| `Event` | Immutable sequenced fact for timeline and replay |

Provider session identifiers remain attempt metadata. They are not the primary
history model.

## Event envelope

Every event contains at least:

- globally unique event identifier;
- run identifier and optional stage, task, and attempt identifiers;
- monotonic database sequence;
- event type and schema version;
- UTC occurrence time and UTC persistence time;
- actor kind and actor identifier;
- correlation and causation identifiers;
- bounded JSON payload;
- optional artifact references.

Sequence defines ordering. Timestamps support diagnosis and presentation but do
not resolve causality.

## Transaction invariants

- A state transition and its event commit atomically.
- A new attempt is committed before an external process starts.
- A retry never mutates the previous attempt.
- Review approval references one exact Git fingerprint.
- Approval consumption and the authorized local state transition commit
  atomically before the external action starts.
- External success is not recorded without provider evidence or reconciliation.
- SignalR notification happens only after commit.

## SQLite design

- Use a file-backed database in the application data directory.
- Enable write-ahead logging after verifying deployment and backup behavior.
- Serialize application writes through one ingestion boundary.
- Keep transactions short and never include child process or network duration.
- Use application-managed concurrency tokens where conflicting updates matter.
- Store canonical timestamps in UTC and avoid depending on SQLite ordering of
  `DateTimeOffset` values.
- Apply EF Core migrations under a single-instance migration lock.
- Create a recoverable database backup before a destructive migration.

The database stores metadata and bounded structured payloads. Large output does
not belong in SQLite.

## Artifact store

Raw transcripts, complete logs, screenshots, patches, generated reports, and
downloaded CI artifacts live beneath an application-owned artifact root.

Each artifact record includes:

- generated identifier;
- content hash and byte length;
- media type and logical purpose;
- run, task, attempt, or check ownership;
- relative storage path beneath the artifact root;
- creation time and retention policy;
- redaction or sensitivity classification.

Paths are generated by the application. User or agent filenames are metadata
only and never determine the storage path.

## Secrets and sensitive data

The database and artifact store must not contain:

- GitHub, Codex, Claude Code, Git, SSH, or package-feed tokens;
- complete child-process environments;
- private keys or credential files;
- secrets extracted from logs;
- unrestricted copies of user home directories.

Provider authentication remains owned by the provider CLI and operating-system
credential store. Redaction is defense in depth, not permission to ingest known
secrets.

## Process ownership and leases

Today, under the current local single-instance deployment, startup reconciles
every durable Process attempt still `Running` to `Interrupted` — the attempt
status alone is the entire test. This is safe because the application runs as
one host process per launch on a local desktop machine, not because any lease,
heartbeat, or process-identity check exists yet: there is no host-instance
identity, no executor lease with acquisition time or expiry, and no heartbeat
recorded for a Process attempt, so reconciliation cannot yet distinguish "this
host crashed" from "a second host instance is genuinely still running this
attempt." Host-instance identity, an executor lease with expiry and heartbeat,
and a stronger reconciliation that checks process identity before concluding an
attempt was interrupted are future capabilities — the executor lease, heartbeat,
and deadline projections of Increment 5, building on the writer lease and
ownership marker introduced for Git worktrees in Increment 3 — not current
behavior.

A separate repository mutation lease prevents two runs from changing worktrees,
shared Git metadata, or publication state for the same canonical repository at
the same time. Its uniqueness is enforced by canonical repository identity, not
display name or user-entered path spelling. Observation-only CI and history work
does not require this mutation lease.

## Startup reconciliation

Startup performs these steps before scheduling new work:

1. acquire the application instance lock;
2. validate and migrate the database;
3. identify non-terminal runs and expired leases;
4. verify worktree existence, ownership marker, branch, HEAD, index, and diff;
5. reconcile attributable child processes;
6. reconcile branch, pull request, and checks by remote identity and head SHA;
7. expire approvals invalidated by state drift;
8. append reconciliation events;
9. expose required recovery choices;
10. schedule only work proven safe to continue.

## Retention and deletion

MVP retention is explicit even for a local tool:

- source repositories are never copied into application data;
- events and decisions are retained until the user deletes a run;
- raw logs and transcripts may use configurable retention because they can be
  large or sensitive;
- deleting a run removes its materialized records and owned artifacts through a
  dedicated operation;
- shared artifacts are reference-counted or prohibited in the MVP;
- database backup retention is documented separately from application deletion.
